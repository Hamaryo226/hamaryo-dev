# ブログ記事を書いて push する

このリポジトリ (`hamaryo-dev`) のブログ記事を、本人のメモから完成形まで持っていくためのスキル。

**想定している使われ方は「出先でスマホから」。** 本人はフリック入力で、長文を打つのも読むのも面倒な状況にいる。
だからこのスキルの肝は、**少ない入力から記事を立ち上げること**にある。
本人が書いた 3 行から、何を話したいのか・何を話しそうなのかを読み取り、こちらから具体的な選択肢を出して埋めてもらう。
「詳しく教えてください」と丸投げするのは、この状況では役に立たない。

## 流れ

1. ネタを受け取る
2. 質問で材料を集める（選択肢形式、1 回で済ませる）
3. 記事を書いて全文を見せる
4. 直す
5. ファイルに落として push

## 1. ネタを受け取る

スキルを呼んだ時点で本人が何か書いていれば、それがネタ。改めて聞き直さない。
何も書かれていなければ、ここだけは短く聞く。

> 何について書きますか。3 行くらいで、思いつくまま書いてください。

同時に、裏で次を調べておく（本人を待たせない）。コマンドは Git Bash / sh 前提。

```bash
git fetch origin                                  # リモートの最新を取る
git ls-tree --name-only origin/main src/content/blog/   # main にある記事番号
git ls-remote --heads origin "blog/*"             # 書きかけの記事ブランチ（番号が予約済みかもしれない）
ls src/content/blog/                              # 今のブランチにある記事番号
date "+%Y年%-m月%-d日"                             # 今日の日付。記事の date にそのまま使う
git status --short                                # 未コミットの変更が無いか
```

記事番号は、この 3 か所のどれかで使われていれば避ける。
`git status` に何か出たら、それは今回の記事と関係ない変更なので、巻き込まないよう本人に伝えてから進める。

## 2. 質問で材料を集める

ネタを読んで、**本人が話しそうなことを先に推測してから**質問する。
ここが一番大事なところなので、手を抜かない。

たとえば「新しいキーボードを買った。打鍵感がいい。値段は高かった」という 3 行なら、
本人が語りそうなのは「なぜ買い替えたのか」「前に使っていたものとの違い」「値段に見合うか」
「プログラミング用途での使い心地」あたり。これを**具体的な選択肢として**提示する。

`AskUserQuestion` で、次の 3〜4 問をまとめて 1 回で聞く。選択肢は必ずネタに合わせて作る。

- **記事の軸** — 何を中心に据えるか。ネタから読み取れる軸を 3 つ書く
  （例:「買い替えた理由と決め手」「実際に使ってみた感想」「値段とのバランス」）
- **触れる話題** — `multiSelect: true` で、推測した論点を 4 つ。本人が「そうそう、それも書きたい」と拾える粒度にする
- **読んだ人にどう思ってほしいか** — 「参考にして選んでほしい」「へえと思ってもらえれば十分」「自分の記録として残す」など
- **分量** — 短め (600字前後・見出し 2〜3 個) / いつもくらい (1000字前後・見出し 3〜5 個) / 長め (1500字前後・見出し 5〜6 個)

選択肢には必ず説明文を付ける。スマホの画面ではラベルだけだと判断できない。

**足りない事実はここで一緒に聞く。** 製品名、価格、バージョン番号、日付といった、
推測で埋めると嘘になるものが必要なら、この 1 回の質問に混ぜて回収する。
あとから小出しに聞くと、そのたびに本人の手が止まる。

## 3. 記事を書く

### 推測していいことと、いけないこと

このスキルの価値は、本人が言っていない部分を埋めることにある。ただし埋めていい範囲は決まっている。

**埋めていい**: 段落のつなぎ、「〜だと感じました」のような感想、話の順序、見出しの言葉、
本人の断片から自然に導かれる考え（「前のものは底打ち感があった」→「長時間打つと疲れやすかった」）

**埋めてはいけない**: 価格、型番、バージョン、日付、スペック、URL、人名、引用。
これらは本人しか知らない。分からなければ質問するか、その話題ごと落とす。
それらしい数字を置くと、本人が気づかないまま事実と違う記事が公開される。

推測で書いた箇所のうち「本人がそう思っているか怪しい」ものは、4 の提示時に印を付けて確認する。

### 文体

既存の 5 記事に合わせる。読み返すのが一番早いので、書く前に 1〜2 本 (`src/content/blog/b03.json` など) を開く。

- です・ます調。「〜と思います」「〜と感じています」で締める段落が多い
- 一人称はほとんど出さない。「私は」を連発しない
- 誇張しない。「最高」「神」のような強い言葉は使わない。良いものは理由とセットで良いと書く
- 1 段落 2〜4 文。スマホで読むので長い段落は作らない
- 技術用語や製品名は原文のまま（`PowerToys`、`Next.js`）。無理に訳さない
- 和文と英数字の間に半角スペースは**入れない**（「Claude Codeで」と詰める）。
  リポジトリの他のドキュメントは空けているが、既存記事 5 本はすべて詰めてある。記事の中で書式が揺れる方が読みにくい

### 構成

既存記事はどれもこの形になっている。踏襲する。

1. `heading` level 2「はじめに」 + `paragraph` 1〜2 個 — 何の話か、なぜ書くのか
2. 本題の `heading` level 2 + `paragraph` — 2 の質問で選んだ話題ごとに 1 セクション
3. `heading` level 2「まとめ」 + `paragraph` 1〜2 個 — 締め

話題を多く選ばれて見出し数が分量の目安を超えるときは、**分量を優先する**。
近い話題どうしを 1 セクションにまとめるか、軽い話題は独立した見出しにせず段落で触れる。
スマホで読む記事が間延びするより、密度がある方がいい。

### 添削

本人が書いた 3 行の言い回しは、**できるだけ残す**。
本人の言葉づかいがその人の記事らしさになる。整えるのは次の範囲にとどめる。

- 話し言葉を書き言葉に（「めっちゃいい」→「とても良い」）
- 主語と述語のねじれ、重複表現を直す
- 1 文が 2 つの主張を含んでいたら分ける

メモが「〜した」「〜になった」のような素っ気ない箇条書きで、残すべき言い回しが無いこともある。
その場合は 2 の質問で本人が選んだ選択肢の言葉を軸にする。選んだということは、その言い方に本人が頷いたということ。

## 4. 全文を見せる

JSON ではなく**読みやすい形で**チャットに出す。本人はスマホで読む。

```
# タイトル案
タグ: Keyboard / Review / Gear
分量: 約 1100 字

## はじめに
（本文）

## 買い替えた理由
（本文）
...
```

推測で埋めた箇所があれば、本文の下にまとめて置く。

```
確認してほしいところ
- 「長時間打つと疲れやすかった」— 前のキーボードの話、これで合っていますか
```

そのうえで「このまま push していいか、直すところがあるか」を聞く。
直す指示が来たら直して、もう一度出す。ここは本人が納得するまで繰り返す。
**承認をもらうまでファイルには書かない。** 承認前にコミットしてしまうと、スマホから取り消すのが面倒になる。

本人に確認できない状況（自動実行やテスト）で動いている場合は、ファイルを作るところまでで止めて、
承認を取れなかったことを報告する。勝手に push しない。

## 5. ファイルに落として push

### 記事番号とファイル

`src/content/blog/` の最大番号 + 1。2 桁ゼロ埋め（`b05.json` の次は `b06.json`）。

`src/content/blog/bNN.json` を作る。**サムネイルは付けない**（`thumbnail` キーごと書かない）。
一覧カードは画像がなくても崩れない。画像は帰宅後に PC から足す。

```json
{
  "title": "記事タイトル",
  "date": "2026年9月20日",
  "description": "一覧カードに出る要約。60〜80 字。記事を読むかどうかの判断材料になる",
  "tags": ["Keyboard", "Review", "Gear"],
  "content": [
    { "type": "heading", "level": 2, "text": "はじめに" },
    { "type": "paragraph", "text": "本文。" }
  ]
}
```

`content` で使えるブロック（型は `src/lib/blogs.ts` の `BlogContent`）:

| type | 書き方 | 使いどころ |
| --- | --- | --- |
| `heading` | `{ "type": "heading", "level": 2, "text": "..." }` | セクションの見出し。level は 2 か 3 |
| `paragraph` | `{ "type": "paragraph", "text": "..." }` | 本文。ほとんどがこれ |
| `list` | `{ "type": "list", "items": ["...", "..."] }` | 理由や項目を並べるとき |
| `code` | `{ "type": "code", "language": "ts", "code": "..." }` | コード。language は `bash`/`ts`/`json` など |
| `link` | `{ "type": "link", "text": "公式サイト（Files）", "url": "https://..." }` | 参照先。URL は本人が出したものだけ |
| `image` | `{ "type": "image", "src": "/thum/xxx.webp", "alt": "...", "caption": "..." }` | 画像。**スマホからは使わない**（ファイルがまだ無い） |
| `embed` | `{ "type": "embed", "platform": "spotify", "url": "https://open.spotify.com/..." }` | Spotify の埋め込み |

`tags` は 3〜4 個。英語の短い語が既存記事の流儀（`Next.js`、`Cloudflare`、`Windows`、`Claude`）。

### 一覧への登録

`src/lib/blogs.ts` を 2 か所直す。ここを忘れると記事は存在するのにサイトに出ない。

```ts
import b06 from "../content/blog/b06.json";   // import の末尾に追加

export const blogs: Blog[] = [
  { ...b06, slug: "06" } as Blog,             // 配列の先頭に追加（新しい順に並んでいる）
  { ...b05, slug: "05" } as Blog,
```

`vite.config.ts` は `getAllBlogSlugs()` を見ているので、追記すれば prerender と sitemap に自動で載る。触らなくていい。

### 確認

壊れた記事を push しないために、最低限ここを見る。

```bash
node -e "require('./src/content/blog/b06.json'); console.log('JSON OK')"
```

`node_modules` があるなら型チェックまでやる（出先だと無いことが多いので、無ければ飛ばしてよい）。

```bash
npx --no-install tsc --noEmit
```

### ブランチを切って push

`main` には直接コミットしない。記事ごとにブランチを切る。

**起点は `origin/main`。** 今いるブランチ（`dev` や別の作業ブランチかもしれない）から切ると、
その作業中のコミットまで記事のブランチに混ざり、記事だけ先にマージできなくなる。

```bash
git checkout src/lib/blogs.ts               # 一覧への登録は一旦戻す
git switch -c blog/06-keyboard origin/main  # blog/<番号>-<内容がわかる英数字>
```

記事の JSON はまだ git の管理下にないので、ブランチを切り替えてもそのまま残る。
ここで switch が「上書きされる」と言って失敗したら、その番号は `origin/main` で既に使われている。番号を取り直す。

`src/lib/blogs.ts` への登録は切り替えたあとにやり直す。
`origin/main` の内容が今のブランチと違うかもしれないので、切り替え後のファイルを読んでから編集する。

```bash
git add src/content/blog/b06.json src/lib/blogs.ts
git commit
git push -u origin blog/06-keyboard
```

コミットメッセージは**日本語 1 行、prefix なし**（このリポジトリの流儀）。
例: `新しいキーボードについてのブログ記事を追加`

末尾に付ける行:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

push したら、PR を作るリンクを本人に渡して終わり。

```
push しました。
https://github.com/Hamaryo226/hamaryo-dev/pull/new/blog/06-keyboard

- src/content/blog/b06.json（新規）
- src/lib/blogs.ts（一覧に登録）

サムネイルは付けていないので、帰宅後に public/thum/ に画像を置いて thumbnail を足してください。
```

`gh pr create` は使わない。PR を作るかどうかは本人が決める。

## つまずきやすいところ

- **記事番号がぶつかる** — 今のブランチだけ見ても足りない。`origin/main` と `blog/*` ブランチの両方を確認する
- **`blogs.ts` の import 忘れ** — JSON を置いただけでは記事は出ない。import と配列の両方を直す
- **配列の末尾に足してしまう** — 新しい順なので先頭。末尾だと一覧の最後に埋もれ、ホームの最新 3 件にも出ない
- **`date` を手で書き間違える** — `date "+%Y年%-m月%-d日"` の出力をそのまま使う
- **ワークツリーが汚れている** — 既に別の変更があるなら、それを巻き込まないよう本人に伝えてから進める
- **記事のブランチに関係ないコミットが入る** — 起点は今いるブランチではなく `origin/main`
- **コマンドが動かない** — 上のコマンドは Git Bash / sh 前提。PowerShell しか無い環境なら `cp` を `Copy-Item`、
  `date "+..."` を `Get-Date -Format "yyyy年M月d日"` に読み替える
